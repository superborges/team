# Codex 页面美化任务说明

## 任务

在当前仓库中，将工时与项目成本系统的现有 MVP 美化为 `DESIGN_SYSTEM.md` 定义的企业蓝风格。保留业务能力、数据接口、状态机、权限和校验，优先复用现有框架与组件库。

先阅读 `DESIGN_SYSTEM.md`、`references/PRD_v1.3_source.md` 的 §3.1、§4.2–4.4、§5.5、§6.1，以及仓库自己的开发约定。`references/approved-visual.png` 只作样式方向；图中数据和按钮不能作为业务真值。

## 第一步：检查仓库

定位填报页、应用导航、日期选择、条目编辑、现场日、送审预览和审批进度组件；查明框架、组件库版本、主题入口、已有 CSS 变量、移动端壳层与业务校验来源。不要在不知道现有结构时另写一套独立产品页面。

输出简短的修改范围和已发现差异后继续做可确认的视觉改造。只有会影响业务或现有交互的歧义才需要阻塞对应修改，其余页面换肤可以继续。

## 第二步：建立主题

将 `tokens.json` / `styles/tokens.css` 映射到现有主题。统一主蓝 `#1664FF`、页面底 `#F5F7FA`、白卡片、6px 控件圆角、8px 卡片圆角，统一按钮、输入、标签、提示和状态。

`components.css` 仅供参考。已有 UI 库优先用其主题能力，不引入第二套库、不写大量全局覆盖或 `!important`。不引入远程字体、CDN 或新的后端依赖。

## 第三步：改造当前填报页面

桌面使用浅色顶栏与按权限显示的导航，填报区最大 1120px。移动端保留原有顶部三项导航，不照搬桌面侧栏。

页面顺序建议为：标题 → 周历 → 当日概览 → 现场日 → 当天记录 → 操作栏。现场日保持独立、显眼；已有现场日默认展开。编辑卡片保留原位编辑，不强制改成每条都要打开弹窗。

概览采用“应填 / 已说明 / 尚差”＋“项目工作 / 非项目工作 / 待分配 / 请假”。明确实际工作是项目与非项目的合计，不将其与子项作为可相加的并列数值。

保留“保存草稿”“预览本周送审”“仅提交当日现场日”“查看审批进度”。只有当前步骤的主操作使用实心蓝。手机固定操作栏注意安全区、最后一条记录和虚拟键盘。

## 不允许随美化变更的内容

- 不把自然周提交改成日提交，不重复提交待审批或已处理条目。
- 不把所有日期写死为工作日或应填 8h，不从设计稿推导真实工作日历。
- 不把待分配计入实际工作、加班或项目成本，不把请假计入已说明。
- 不把“填报完整”等同于“审批通过”。
- 不移除现场事由、单独送审与零工时现场日能力。
- 不新增普通员工的成本、费率和管理权限，不在 CSS 层代替权限控制。
- 不把工作日基数、上限、红标阈值、步长硬编码为设计变量。
- 不新增自动保存、撤回、自动确认待分配等未经确认的行为。
- 不直接采纳此前 review 中尚未确认的业务建议；例如实际工作内容重复校验保持已确认规则。

## 第四步：验证

先运行现有 lint、类型检查和测试，再验证以下场景：

1. 在 320、375、390、768、1024、1440px 检查页面，无全局横向滚动；桌面与移动端分别截图。
2. 4h 项目＋1h 部门事务＋3h 待分配的汇总正确；请假不重复计入；基数 0 不除零。
3. 草稿、待审批、已通过、已驳回、封账待审批、加载、空态和接口失败均有正确呈现。
4. 实际编辑、保存失败后重试、周送审预览、独立现场日送审与审批进度仍可使用。
5. 键盘操作、焦点、必填错误、长对象名称、三条以上记录、底部安全区正常。
6. 在目标企业微信真机容器中检查免登返回、页面高度、键盘遮挡和返回操作。本设计包未验证这些环境行为。

如果无法运行某项检查，明确说明原因；不要把“浏览器静态预览通过”写成“业务回归全部通过”。

## 完成时输出

汇总修改文件、抽取组件、主题接入点、桌面/移动截图、已执行的测试及结果，以及仍存在的业务歧义。避免借机重构后端、改表结构或扩展需求。
