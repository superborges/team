## 1. 背景与目标

### 1.1 现状问题

当前员工日报填报在 WPS 多维表格中进行，存在三个结构性问题：

1. **无审核闭环**：填报后无人审核，数据真实性无保障
2. **无成本口径**：日报只记录"做了什么"，无法换算为项目人工成本
3. **数据无出口**：填报数据从未产出过管理层可用的报表，员工感知不到填报价值

导致的直接后果：项目人工成本不清、人员工作负荷不清。

### 1.2 系统目标

**已确认的管理目标**：项目投入管理与人员调配同等重要。项目视角关注各项目消耗的标准成本及时间；人员视角关注项目工作、非项目工作与待分配时间的构成。填报完整度、审批进度与实际工作负荷分别呈现。

| 目标 | 衡量指标 |
|---|---|
| 工时数据真实可用 | 填报及时率 ≥ 95%，审批完成率 ≥ 95% |
| 项目投入可按标准成本核算 | 每月可产出全量项目标准人工成本与标准现场成本报表 |
| 人员负荷可视 | 每周可产出人员负荷热力图，识别持续超载与已确认的待分配时间；漏填、待审批另行标识 |
| 填报体验不成为阻力 | 员工单日填报耗时 ≤ 3 分钟 |

填报及时率与审批完成率衡量流程执行情况，不能单独证明数据真实；实际投入及项目归属通过审批核实，分歧按 4.5 处理。

### 1.3 设计原则

- **窄而深**：v1 只做工时与成本，不做任务管理、WBS、里程碑
- **成本动因正确**：每一笔成本按其真实动因归集，不做人为平摊
- **暴露问题而非抹平问题**：报表设计的目的是让管理层看到异常，而不是让数字好看
- **机制优先于工具**：系统设计需服务于"填报—审批—报表—管理动作"的闭环，缺任一环工具都无效

### 1.4 非目标（v1 明确不做）

- 任务管理、WBS 分解、里程碑跟踪
- 合同额、项目预算、毛利核算
- 差旅报销单据、实际报销金额
- WPS 多维表格历史数据迁移
- 真实薪酬数据接入

## 2. 用户角色与权限

### 2.1 角色定义

| 角色 | 说明 |
|---|---|
| 普通员工 | 填报本人工时 |
| 项目经理（PM） | 审批本人负责项目的工时，含售前 PM、实施 PM、研发 PM；查看统一职级费率及本项目人员工时、标准成本明细 |
| 部门负责人 | 部长、副部长。审批本部门内部杂活工时、确认待分配时间；按本人回避规则承接相关记录；查看本部门人员负荷；**查看本部门为主责单位的项目成本** |
| 分管领导 | 审批跨部门杂活工时（分管市场 / 分管技术）；承接本人回避至分管领导的项目或非项目记录 |
| 公司领导 | 查看全公司报表；被指定时承接无法逐级找到合适审批人的记录，仍须回避本人 |
| 系统管理员 | 维护主数据、费率、审批规则 |

角色可叠加：一名员工可同时是普通员工、某项目 PM、某部门负责人。

### 2.2 权限矩阵

| 功能 | 员工 | PM | 部门负责人 | 分管领导 | 公司领导 | 管理员 |
|---|---|---|---|---|---|---|
| 填报本人工时 | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| 查看本人工时与负荷 | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| 审批所辖或被指定的待办 | — | ✓ | ✓ | ✓ | ✓（仅指定待办） | — |
| 查看本项目标准成本及人员明细 | — | ✓ | — | — | ✓ | ✓ |
| 查看本部门主责项目成本 | — | — | ✓ | ✓ | ✓ | ✓ |
| 查看本部门人员负荷 | — | — | ✓ | ✓ | ✓ | ✓ |
| 查看全公司报表 | — | — | — | — | ✓ | ✓ |
| 查看费率标准 | — | ✓ | ✓ | ✓ | ✓ | ✓ |
| 维护费率与主数据 | — | — | — | — | — | ✓ |
| 授权解锁已封账记录或补录范围 | — | — | ✓ | ✓ | — | ✓ |

**费率与成本可见性（已确认）**：仅具普通员工角色的人员只查看本人工时与负荷，不显示费率或成本金额。PM 可只读查看统一职级费率标准（含生效版本），并查看本人负责项目的人员工时、采用的标准费率及标准成本明细，包括跨部门参与人员在该项目中的投入；项目汇总、人员汇总与条目明细保持同一查看范围。PM 不因此取得其他项目的成本明细权限。这里的费率是管理用的标准费率，真实薪酬仍不接入；费率维护权限仅归管理员。多角色人员按其已有角色授权执行。

**部门负责人成本可见范围**：以 `work_item.owner_dept_id`（主责部门）为判定依据，部长与副部长可见本部门为主责单位的全部项目成本，含项目下所有参与人的工时与成本明细（**不区分参与人所属部门**——跨部门支援本部门项目的人员工时同样可见，否则部门主责项目的成本是残缺的）。部门负责人不可见本部门人员在其他部门主责项目上产生的成本金额，仅可见其工时数量（用于负荷管理）。

**部长与副部长权限一致**，均为部门负责人角色，不做层级区分。

**回避与转交待办的审批权限**：按 4.1 指定的实际审批人可查看并处理分配给自己的审批包，包括包内工时与现场日。该授权限于此包，不因此获得该项目其他人员的记录或整个项目的成本报表权限；已有部门及项目报表权限仍按上述规则执行。管理员执行配置与转交，不因管理员身份获得业务审批权。

## 3. 核心概念与数据模型

### 3.1 核心抽象：工时归集对象（WorkItem）

系统将所有可填报工时的对象统一抽象为 **WorkItem**，分两大类：

**项目类（计入项目成本）**
| 子类型 | 数据来源 | 默认审批人 |
|---|---|---|
| 营销项目 | OA 立项接口同步，手工导入兜底 | 售前 PM |
| 实施项目 | OA 立项接口同步，手工导入兜底 | 实施 PM |
| 研发项目 | OA 立项接口同步，手工导入兜底 | 研发 PM |

**非项目类（实际非项目工作、待分配时间与请假记录，不计入项目成本）**
| 子类型 | 归属判定 | 默认审批人 |
|---|---|---|
| 部门内事务（内部会议、部门材料、内部技术交流等） | 单一部门 | 该部门负责人 |
| 跨部门·市场类（外出考察、市场支持、上级职能部门材料等） | 跨部门 | 分管市场领导 |
| 跨部门·技术类（技术交流、技术预研、标准编制等） | 跨部门 | 分管技术领导 |
| 学习培训 | 单一部门 | 该部门负责人 |
| 待分配时间（没有任务安排） | 员工所属部门 | 该部门负责人 |
| 请假 / 休假 | 系统自动 | 无需审批（OA 已审批） |

**时间口径**：实际工作工时包括项目工作、因项目出差的交通投入及上述实际非项目工作，反映人员实际被占用的时间，不直接等同于产出或效率。出差交通按 5.2 归集到相应项目，同一段时间只计一次。待分配时间由员工如实记录、部门负责人确认，用于人员调配，不计入实际工作工时、加班或项目成本。请假记录仅用于展示出勤信息、扣减应填基数，不计入填报时间合计、实际工作工时或项目成本。

> **设计说明**：杂活必须在系统内建为实体对象，不能让员工自由填写文本。原因有二：一是文本无法聚合统计（这正是当前多维表格失效的原因之一）；二是审批人必须由对象决定，自由文本无法路由。杂活对象由管理员或部门负责人预先创建并维护，员工只能选择，不能新建。

## 4. 审批路由设计（核心）

### 4.1 路由原则

**默认审批人由“工时归集对象”决定，所有人工审批均回避本人。** 每个 WorkItem 上挂载唯一的 `approver_user_id`，作为默认路由。普通成员的项目记录仍由该项目默认审批人处理。这样做的好处：

- 跨部门项目天然支持（员工做别部门项目，审批人自然是该项目 PM）
- 新增项目类型或杂活类型时，只需配置数据，不需改代码
- 审批人变更（如 PM 换人）更新对象默认审批人，对之后新生成的审批包生效；已生成待办按下述转交规则处理，历史审批不改写

管理员手工创建 WorkItem 时，系统按 3.1 表中的规则**推荐**默认审批人，允许手工调整。OA 同步项目的默认审批人随来源 PM 同步，遵守 6.3 的核心字段维护规则；本人回避或临时代办通过实际审批人和转交记录处理。

**项目本人记录回避（已确认）**：

1. 读取项目默认审批人；若其与填报人不同，直接由该审批人处理。
2. 若项目默认审批人就是填报人（例如 PM 填报自己负责的项目），转交**填报人所属部门**的指定部门负责人。
3. 若该指定部门负责人仍是填报人，转交该部门指定的分管领导。

- 工时与现场日使用同一规则；即使现场归属项目当日工时为 0，该现场日仍须按上述规则送审。
- 部门有多名负责人时使用管理员配置的指定负责人，不随机选人或同时推送多人审批；分管领导同样明确配置。
- 回避只改变这名填报人的审批包接收人，**不修改项目上的默认审批人**。PM 参与别人负责的项目时，仍由那个项目的默认审批人审批。
- 实际审批人确定后写入 `approval_package.approver_user_id`，记录默认审批人、实际审批人与回避原因；待办、提醒、通过和驳回操作均使用包内实际审批人。
- 指定负责人或分管领导缺失、无效，或最终审批人仍为本人时，执行下述公司指定规则；指定完成前保留数据并提示处理，不回退自批或自动通过。

**非项目本人回避与审批兜底（已确认）**：

- 非项目工作、待分配时间等需要人工确认的记录同样回避本人。部门负责人填报由自己审批的部门事项时，转分管领导；分管领导本人或无法逐级找到合适审批人时，由公司指定另一名非本人负责人。
- 公司指定由业务方确定接收人，管理员登记到对应人员或对象的审批配置。指定人须有效且不为填报人，授权仅覆盖被指定的记录，不新增其全公司审批权限。
- 请假记录依据 OA 已有审批自动确认，不重复发起人工审批；需人工处理的例外不能借此绕过本人回避。

**缺席、离职与在途审批交接（已确认）**：

- 原审批人缺席或离职时，由业务方指定合适接收人，管理员执行转交。转交前同样校验接收人有效、具备本次业务授权且不是填报人。
- 转交仅改变尚未处理待办的实际审批人；已处理条目的审批结论、原处理人和时间不变。记录原审批人、新审批人、业务指定依据、操作人、转交时间及原因。
- 转交完成后，待办、提醒和审批操作权限以新接收人为准，原接收人不再处理已转出的未决记录。长期职责调整还需更新对象默认审批人，临时代办不改长期配置。

**验算场景**：A 项目 PM 张三属于技术部。李四填报 A 项目，由张三审批；张三填报 A 项目，由技术部指定负责人审批；若技术部指定负责人也是张三，则由技术部分管领导审批。张三填报由王五负责的 B 项目，仍由王五审批。

### 4.2 审批包拆分逻辑

一名员工一周的工时通常涉及多个对象，对应多个审批人。因此提交时按对象拆包：

```
员工提交某自然周记录（周一至周日）
  → 同时收集工时条目与现场日，按 work_item_id 分组
  → 读取对象默认审批人，所有人工审批按 4.1 执行本人回避
  → 每组生成一个 approval_package，保存实际审批人
  → 分别推送给各包的实际审批人
```

**示例**：张三本周工时为「A实施项目 20h、B研发项目 12h、部门内部会议 4h、技术交流 4h」，提交后生成 4 个审批包，分别推送给 A 项目实施 PM、B 项目研发 PM、本部门负责人、分管技术领导。每位审批人只看到自己对象下的工时，看不到其他对象。

待分配时间按所属部门的预置对象生成审批包，由该对象配置的部门负责人确认。请假/休假记录不生成审批包，直接置为已通过，但不计入工作工时或填报时间合计。

**现场日的特殊处理**：若员工当周存在现场日，需按现场归属项目及 4.1 本人回避规则，向实际审批人生成现场日审批项，**即使当日全部项目工时均为 0，或整周只有现场日而没有工时条目，也必须生成审批包**（详见 5.5）。若该项目当周已有可合并的待审批包，现场日审批项合并呈现；已处理条目不因补报现场日重新变为待审批。

### 4.3 状态机

```
草稿(draft) ──提交──> 待审批(pending) ──通过──> 已通过(approved) ──封账──> 已锁定(locked)
待审批(pending) ──驳回──> 已驳回(rejected) ──修改──> 草稿(draft)
已通过 / 已锁定 ──获准更正（封账后须授权解锁）──> 草稿（更正版本）──提交──> 待审批
```

- 驳回粒度到**条目级**：审批人可只驳回包内某几条，其余通过，包状态置为"部分驳回"
- 被驳回条目在修改时回到草稿，员工修改后单独重走审批，不影响已通过条目
- 已通过条目员工不可直接修改，需申请审批人打回；封账后的更正还须先取得解锁授权。更正版本不覆盖已发布月报内的原始记录及成本快照
- 解锁只开放指定记录或补录范围的处理权限，不代表业务审批通过。待审批记录获准补审后继续原审批流程；需要修改的记录重新提交审批；修订完成后按 6.6 重新锁定并生成新月报版本
- 工时与现场日都受月份封账约束；未决条目保留原审批状态，不因封账自动通过，未获授权不得补审或更改

### 4.4 提交与审批节奏

按自然周（周一至周日）归集。员工按发生日期填报，次周提交完整的上周记录，覆盖周末加班、交通投入与现场驻留，不要求预填尚未发生的工作。

| 环节 | 时间 | 规则 |
|---|---|---|
| 员工填报 | 每个工作日 | 当日填报，最晚次日 12:00 前补填 |
| 员工提交 | 次周一 12:00 前 | 周一 10:00 提醒尚未提交上周记录者；截止后自动提交符合校验的未提交草稿，并标记“逾期提交” |
| 审批 | 次周三 18:00 前 | 次周一 14:00 推送待办；超时未审批推送二次提醒并抄送其上级 |
| 封账 | 每月 10 日 00:00 | 封闭上月，已确认工时与现场日一起锁定；未决数据单列，生成正式月报版本，详见 6.6 |

自动提交执行与手动提交相同的日级校验、本人回避和封账限制，只处理目标自然周的未提交记录。未通过校验的草稿保留并提醒补齐，不自动补足工作或待分配时间；符合独立送审条件的现场日可单独生成审批包。已提交或已处理条目不重复提交。以上时间点均按 6.5 配置管理。

### 4.5 审批事实与工时争议处理（已确认）

**审批确认实际发生的投入及其项目归属，效率问题另行复盘。** 员工确实投入 8 小时，即使 PM 认为合理耗时应为 4 小时，也不能仅因此将实际工时压减为 4 小时或转记为杂活。若填报存在事实错误或项目归属错误，则依据核实结果更正并留痕。

- 对双方无法确认的工时或项目归属，由**项目主责部门负责人**协调。此处按项目主责部门确定，与本人回避时按填报人所属部门确定负责人不同。
- 涉及跨部门且协调不能达成一致时，由**分管领导裁定**。
- 协调与裁定人员按职责查看相关争议记录和依据，授权限于所处理的争议；系统管理员维护配置，不代替业务负责人作事实裁定。
- 争议处理仅针对争议条目，不为所有工时增加部门负责人或分管领导的例行审批环节，也不阻塞同包其他无争议条目的正常审批。
- 保留原始填报、双方说明、协调或裁定结论、处理人、处理时间及处理原因。不得直接覆盖原始记录；需要更正时保留修改前后内容，并按审批与封账规则处理。
- 未解决的争议条目单独标明处理状态，不能视为已经确认的项目成本；人员负荷同时提示存在未决数据，不能把未确认工时当作闲置。协调或裁定后的处理结论与最终审批记录保持可追溯。

**验算场景**：员工填报 A 项目 8 小时。若双方确认确实发生且归属于 A，8 小时据实计入，效率问题另行复盘；若实际投入或归属仍有分歧，则交 A 项目主责部门负责人协调，跨部门协调不成再交分管领导裁定，原始 8 小时填报与最终处理结果均保留。

## 5. 成本模型（核心）

### 5.1 两笔独立成本

**成本性质（已确认）**：本系统核算按统一费率折算的项目投入，报表使用“标准人工成本”“标准现场成本”“标准总成本”。这些金额用于项目资源消耗比较与投入管理，不代表实际薪酬支出、实际差旅报销或完整财务成本。

项目成本由两个成本项构成，**各自按自己的成本动因归集，互不平摊**：

```
项目标准总成本 = 标准人工成本 + 标准现场成本

标准人工成本 = Σ(已审批项目工时 × 工作发生日有效的职级小时费率)
标准现场成本 = Σ(已审批现场天数 × 现场发生日有效的现场日成本标准)
```

### 5.2 设计依据

现场发生的额外费用（交通、住宿、补贴）的成本动因是**"这个人去了一趟现场"**，与他到达现场后每小时做什么无关。因此：

- 人工成本按工时归集，**不乘任何现场系数**
- 现场成本按因项目出差的自然日全额归集到**出差事由对应的项目**，每天最多一次；交通日、必要驻留和半天出差的计数规则见 5.5

**典型场景验算**：员工当日在 A 项目现场工作 12 小时，其中 4 小时为 A 项目、8 小时为 B 项目。设该员工中级职级 150 元/小时，现场日成本标准 800 元/天。

| 项目 | 人工成本 | 现场成本 | 合计 |
|---|---|---|---|
| A（出差事由项目） | 4 × 150 = 600 | 800 | 1400 |
| B | 8 × 150 = 1200 | 0 | 1200 |

A 项目 PM 只承担自己实际消耗的 4 小时人工，加上确实为其发生的一天差旅；B 项目不承担差旅，因为这 8 小时的工作在公司同样能完成。双方均无争议。

> 若采用"现场工时 × 系数"的模型，A 项目 PM 将被迫承担 12 小时的加权成本，这既不符合成本动因，也必然引发审批争议。

**出差交通工时与归属（已确认）**：

- 因项目发生的交通时间计入出差事由项目的实际投入，按该员工工作发生日的职级与标准费率计算人工成本，内容注明“出差交通”及出差事由。
- 交通途中若实际为另一项目工作，对应时段归到实际工作的项目，剩余交通时间归出差事由项目；同一段时间不能同时作为交通工时和另一项目工作工时重复归集。
- 交通工时按实际发生时间填报，不根据现场天数自动补成 8 小时。周末实际赶路按 5.3 的非工作日加班口径记录；周末仅因项目需要驻留休息，不产生工作工时。
- 交通占用的人员时间产生标准人工成本，出差自然日产生标准现场成本，两项按各自口径独立计入；现场日仍为每人每天最多一次。

**交通场景验算**：同一天因 A 项目赶路 6 小时，到场后为 A 工作 2 小时。

| 情况 | A 项目工时 | B 项目工时 | 当日投入合计 | 现场日归属 |
|---|---|---|---|---|
| 途中没有处理其他项目工作 | 交通 6h + 到场工作 2h = 8h | 0h | 8h | A 项目 1 天 |
| 6h 交通期间有 2h 实际为 B 工作 | 剩余交通 4h + 到场工作 2h = 6h | 2h | 8h | A 项目 1 天 |

### 5.3 加班工时规则

- 单日填报上限 24 小时
- 工作日实际工作工时超出 8 小时的部分自动标记为加班；非工作日实际工作工时全部计为加班，含因项目发生的交通投入。待分配时间、请假及仅驻留休息均不参与加班计算
- 单日实际工作工时超过 16 小时的记录，在填报页、审批页、报表中**统一红色标注**，提示审批人重点核实
- **加班工时费率系数为 1.0**，与正常工时同价
- 设计理由：若加班费率高于正常费率，将直接激励员工虚报加班以抬高个人"贡献值"，同时使项目成本失真。加班信息通过报表单独呈现给管理层，用于负荷管理，而非用于成本放大。

### 5.4 费率生效与成本快照

- 费率表按 `effective_from / effective_to` 管理版本，历史费率行**只读**
- 工时以**工作发生日 `work_date`**确定当日有效职级及其费率，在审批通过时计算金额写入 `cost_snapshot`；审批日期只决定固化时点，不决定计价标准
- 现场日同样以现场发生日确定有效现场日标准，审批通过时固化金额
- 职级变更保留生效历史。审批时记录采用的职级、生效费率版本与金额，确保可追溯；若缺少工作发生日的有效职级或费率，提示补齐后再通过，不使用当前标准代替，也不按零成本处理
- 后续员工调级或费率调整，**不回溯修改历史成本**。封账后获准更正时仍按工作发生日的有效职级与费率处理，新结果进入修订版本，不覆盖原已发布版本

**验算场景**：8 月 31 日产生的工时，9 月 1 日费率调整，9 月 3 日审批。该笔工时仍使用 8 月 31 日有效的职级与费率，不因审批延迟而涨价。

> 无成本快照将导致：某人从中级调为高级后，其过去两年所有项目的历史成本被自动改写，已上报过的报表数字全部对不上，系统公信力归零。

### 5.5 现场日口径与真实性保障（不做 OA 前置校验）

**现场日计数口径（已确认）**：按“因项目出差的自然日”核算标准现场成本，以 `user.id + 日期` 唯一计数。

| 场景 | 计数与归属 |
|---|---|
| 去程、返程当天主要在交通途中 | 去程日、返程日各计 1 天；若为同一天，合计只计 1 天 |
| 因项目需要在周末继续驻留，没有工作 | 计 1 个现场日，允许工作工时为 0 |
| 半天到场或当天往返 | 统一计 1 天，不按半天折算 |
| 同一天服务两个或多个项目 | 全日仅计 1 天，归主要出差事由项目，不按项目重复计费或平摊 |
| 因私人原因延长停留 | 私人延长的日期不计项目现场日，即使地理上仍在出差地 |

- 上述天数按现场发生日的统一日标准计价，是标准成本估算，不逐日核对实际住宿、交通或补贴金额。
- **现场日与工作工时独立**：可以只有现场日而没有工作工时，审批后产生现场成本；系统不因此自动生成工作或加班工时，也不自动将交通、驻留记成待分配时间。
- 出差交通时间按 5.2 另填项目投入。仅申报现场日不自动减少应填基数或认定当日时间已填完整，不能用现场日替代应记录的交通工时。

**验算场景**：员工因 A 项目周五出发、周一返回，周末因项目需要继续驻留且没有工作。符合条件并审批通过后计 4 个现场日；周末可没有工时条目。若周末停留纯属私人安排，则这两天不计项目现场日。

**真实性校验：v1 不与 OA 出差申请单做前置比对校验。**

**不做前置校验的原因**：员工出差常在返程后才补填 OA 出差单，OA 数据虽准确但严重滞后。若填报时强制比对，将大量误伤诚实填报者——出差当天填报现场，系统却因 OA 无单而阻断。填报体验受损是此类系统的首要失败原因，为防范少数造假而阻断多数正常填报，代价不划算。

**替代方案：把核实责任交给最有动机、也最有信息的人。**

现场日成本 100% 归属于出差事由项目，该项目 PM 负责核实此人当天是否因该项目出差、在途或需要继续驻留；PM 本人记录按 4.1 回避。因此设计如下强制规则：

**现场日必须进入按现场归属项目及 4.1 本人回避规则确定的实际审批人审批包，即使当日全部工作工时为 0。** 普通成员由现场归属项目 PM 审批；PM 本人记录由其所属部门指定负责人或分管领导审批。

- 员工标记某日为「现场 + A 项目」时，系统在生成审批包的同时，**必定**向按上述规则确定的实际审批人生成一条现场日审批项
- 审批项内容：日期、员工、现场归属项目、现场事由说明、标准现场成本、**当日该员工在本项目的实际工作工时 / 当日实际工作总工时**（不含待分配与请假），并标明当前确认状态；总工作工时为 0 时比例显示“不适用”，不触发低占比提示
- 审批人可单独驳回现场日（不影响该日工时条目的审批）
- 驳回后该现场日成本不计入项目

> **为什么必须在工时为 0 时也生成审批项**：否则会出现漏洞——员工挂着 A 项目的现场日，当天干的全是 B 项目的活，A 项目因无工时而不生成审批包，A 的 PM 永远看不到这笔已经计入他成本的 800 元。这是本设计中最容易被开发遗漏的一处，需在评审时重点确认。

**事后核查手段（自动化比对）**：

苍穹出差申请单数据已确认可通过接口获取。虽然不用于前置校验，但可用于**月度自动比对**：

- 每月封账前，系统自动拉取上月出差申请单，通过工号解析为本系统 `user.id` 后，按「user.id + 日期」与现场日记录比对；身份无法匹配时单列同步异常，不误判为“OA无单”
- 出差单按覆盖的自然日展开比对，包含交通日与周末；同一人员同日多单不重复生成现场成本。比对提示不能代替对主要出差事由、因项目驻留及私人延长的核实，不依据 OA 日期范围自动补记现场日
- 比对结果三态：`一致`（当日有出差单）、`OA无单`（现场日无对应出差申请）、`OA有单未填现场`（可能漏填，同样是问题）
- 若苍穹出差单包含项目编码，额外比对项目归属是否一致，不一致标记为 `项目不符`
- 异常记录汇总至「现场日台账」报表，管理员与部门负责人可查看
- **比对结果仅作提示，不自动扣减成本、不自动驳回**

> 这样处理的关键在于：把 OA 数据的滞后性排除在填报流程之外，只在月度回看时使用。员工填报时不受任何阻断，但月底任何异常都会被自动列出来。既保住了填报体验，又让虚报无处可藏。

后续若比对发现实际存在虚报，再评估引入前置校验或定位打卡等强手段。

## 6. 功能需求

### 6.1 工时填报（P0）

**入口**：企业微信工作台应用，移动端与 PC 端均需支持。移动端为主要填报场景。

**填报流程（两步）**：

*第一步：设置当日地点*
- 选择「在司」或「现场」
- 页面说明「现场」包含因项目出差的交通日与必要驻留，按自然日计现场成本，不要求当天有实际工作
- 选「现场」时必须选择**现场归属项目**（一天有且仅有一个）
- 现场归属项目下拉列表优先展示该员工当前参与的项目
- 现场日提交后生成一条 `onsite_day` 记录，同一人员同一日期最多一条；重复提交不重复计费
- **允许单独提交现场日**：工作工时为 0 时可不添加工时条目，仅填写现场归属项目与现场事由后送审。现场日入口在周末、节假日及全天请假日仍可使用，是否符合项目出差条件由审批人核实

*第二步：填写工时明细*
- 逐条添加：选择工时归集对象 + 填写小时数 + 填写工作内容
- 出差交通选择出差事由项目，内容注明交通及事由；途中处理其他项目工作的时间先归实际工作项目，剩余交通时间再归出差事由项目，同一时段不重复填报
- 小时数按 **0.5 小时步长**，快捷按钮提供 1h / 2h / 4h / 8h
- 对象下拉列表按「我的项目 → 我的部门杂活 → 全部」三段排序，支持搜索
- 实际工作条目的工作内容必填，不少于 10 字，禁止与前一日内容完全重复
- 当天没有任务安排的时间可选择「待分配时间」，由本部门负责人确认。页面显示尚未说明去向的时间差额，由员工确认后记录，不自动将漏填补成待分配
- 待分配条目可使用预置说明“暂无任务安排”，允许补充原因，不套用实际工作内容的最少字数与重复校验

**已确认的填报示例**：当日应填 8 小时，员工记录项目工作 4 小时、部门事务 1 小时、待分配 3 小时。填报时间合计为 8 小时，实际工作工时为 5 小时，项目成本仅按 4 小时项目投入核算；3 小时待分配用于负责人调配工作。

**校验规则**：

| 规则 | 处理 |
|---|---|
| 实际工作工时 + 待分配时间 < 应填基数 | 阻断提交，提示尚未说明去向的差额；员工可补录真实工作或确认待分配时间，不要求将差额填成工作 |
| 单独提交现场日 | 不受工作工时最低基数校验阻断；仅送审现场日，不代表当日工时已完成，也不自动生成工时或调整基数 |
| 当日填报时间合计 > 24 小时 | 阻断提交 |
| 当日实际工作工时 > 16 小时 | 允许提交，**红色标注**并要求填写说明；审批页同步红色高亮 |
| 单条工时 > 8 小时 | 警告但允许 |
| 实际工作条目的工作内容 < 10 字 | 阻断提交；待分配条目采用上述专用说明规则 |
| 请假日 | 自动扣减应填基数，全天请假无需填报工作工时；确有符合条件的现场日仍可单独申报，不因有请假单自动认定现场日有效 |
| 非工作日 | 无实际工作或交通投入则无需填报工作工时；因项目需要的现场日仍须申报。实际工作及出差交通工时全部计为加班，待分配与仅驻留休息不计为加班 |

**便捷功能**：
- 复制昨日：一键复制上一工作日的填报结构（对象与小时数），实际工作内容需重新填写；待分配时间须重新确认
- 常用对象置顶：按近 30 天使用频次排序

### 6.2 工时审批（P0）

**入口**：企业微信应用「待我审批」，PC 端为主要审批场景。

**审批视图**（按周 × 按对象聚合）：
- 「待我审批」按审批包的实际审批人加载，支持项目及非项目本人回避、公司指定和在途转交；页面显示相应回避或转交原因
- 顶部：对象名称、被审批人、周区间、合计工时、本周该对象总工时
- 列表：按日期展开的工时条目，含日期、小时数、在司/现场标记、工作内容
- 部门负责人审批待分配时间时，确认当天是否缺少任务安排，作为人员调配依据；待分配与实际工作分开汇总
- 现场日区块：单独列出本包内的现场日审批项，显示日期、现场事由说明、标准现场成本、当日本项目实际工作工时/实际工作总工时及确认状态，可单独通过或驳回；支持只有现场日、合计工作工时为 0 的审批包
- 操作：整包通过 / 逐条勾选通过 / 逐条驳回（驳回必填原因）
- 争议条目关联原始填报、双方说明与协调/裁定结论，按 4.5 处理；最终审批留存处理依据
- 单日实际工作工时超过 16 小时的记录红色高亮
- 辅助信息：显示该员工本周在其他对象上的**工时总量**（不显示具体对象名称，用于判断合理性，同时避免跨项目信息泄露）

**审批人视角的成本可见性**：PM 可见本包各条工时采用的职级标准费率、标准人工成本及汇总，现场日显示相应标准现场成本。未审批金额明确标为试算，按工作发生日有效标准计算；已审批或已锁定记录显示固化的成本快照，不能用当前费率重新计算历史金额。

### 6.3 主数据管理（P0）

**项目主数据（接口同步为主，手工兜底）**
- **主路径**：通过苍穹接口每日自动同步项目立项信息（详见《接口需求规格书》）
- **兜底路径**：管理员可通过 Excel 模板批量导入，可单条手工新增与编辑
- 同步字段中，`project_type`（营销/实施/研发）需通过**类型映射表**从苍穹项目类型字典转换，映射表由管理员维护
- 接口同步的项目，本系统内**不可修改核心字段**（编码、名称、主责部门、PM），修改需回到苍穹；本系统可补充维护苍穹没有的字段（如是否参与工时核算）
- 手工创建的项目标记 `source = 手工`，与同步项目并存互不覆盖
- 同步异常（如 PM 工号在本系统无匹配人员）进入「同步异常列表」，管理员手工处理，不阻塞其余数据同步

> **两条路径必须同时保留**。接口由信息部门排期开发，存在交付与联调周期；开发阶段用 Excel 导入即可跑通全部业务逻辑，接口就绪后切换数据源。若删掉手工路径，接口延期将直接阻塞整个项目。

**杂活对象管理**
- 管理员与部门负责人可创建、编辑、关闭杂活对象
- 创建时选择子类型，系统按规则推荐审批人，可手工调整
- 需预置一批常用杂活对象，避免上线初期员工无对象可选
- 每个部门预置「待分配时间」对象，指定部门负责人确认，不计入项目成本

**人员与组织（v1 以管理员手工维护为主）**

分公司新成立，部门划分、部门名称、部长与副部长人选均处于变动期。v1 采用**本系统内独立维护**方案：

- 部门树的增删改、改名、调整层级，由管理员在系统内完成
- 部门负责人（部长 / 副部长）由管理员指派，支持一个部门配置多人，变更时按生效区间新增记录
- 每个部门明确配置本人回避时的指定部门负责人及分管领导；负责人多名时只指定一位承接，不按角色名称自动推断顺序。无法逐级承接的人员或对象按公司业务指定登记另一名负责人，缺席或离职待办按 4.1 留痕转交
- 人员的部门归属、职级由管理员维护，支持 Excel 批量导入与批量调整；职级调整必须记录生效日期并保留历史
- 人员基础信息（姓名、企微 UserID、在职状态）从企业微信通讯录同步，工号复用现有身份体系中已打通的关联取得，**仅同步人员身份，不同步组织结构**
- 人员导入、查询与匹配均将工号按字符串处理，支持两种既有格式；工号变更与身份资料更新保持内部 `user.id` 不变。离职人员停用，保留历史业务记录
- 提供「组织变更」批量操作：部门合并、拆分、整建制人员划转

**与企业微信的关系**：`wecom_dept_id` 字段保留，作为未来自动同步的挂接点，v1 不启用自动同步。

> **为什么 v1 不同步组织结构**：企微通讯录的调整由行政或 HR 发起，时点与本系统的报表口径不一致。若自动同步，可能出现"月中部门重组，导致上半月已审批的工时突然归到了新部门"的情况，报表数据会在无人操作的情况下自行变化。手工维护虽然多一点工作量，但组织变更的时点可控，报表口径稳定。待组织稳定后再评估是否开启自动同步。

**组织变更对历史数据的处理原则**：
- 已审批工时的部门归属**在生成时快照落库**，不随后续组织调整回溯变化
- 部门改名：在线分析可显示新名称（因 code 不变，视为同一部门）；已发布月报保持版本内保存的名称，保证原版可复现
- 部门合并 / 拆分：管理员操作时需明确指定历史数据的归属处理方式，系统留痕；涉及已封账月份的更正按 6.6 处理，不直接改写已发布月报

**费率管理**
- 管理员维护职级费率表与现场日成本标准
- 修改费率为新增生效区间，不覆盖历史行

### 6.4 报表（P0，上线首月必须可用）

> 报表是整个闭环的动力来源。若数据填了却无人看，系统必然重蹈多维表格覆辙。以下五张报表为必交付项。

**报表一：人员负荷热力图**
- 维度：人员 × 周（可切换到日）
- 数值：已审批实际工作工时 / 应填工时；实际工作包括项目工作、因项目出差的交通投入及非项目工作，不包括待分配时间、请假与仅驻留休息。已锁定记录仍计入已审批数据
- 同时显示项目工作、非项目工作、已确认待分配时间，以及填报完整度和审批进度；待分配时间供负责人进一步核实、调配，不直接等同未来可用工时
- 色阶：数据完整且审批完成时，< 80% 蓝色（工作投入较低，结合待分配时间判断）、80-110% 绿色、110-130% 黄色、> 130% 红色（超载）
- 数据未填完整、存在待审批或驳回未处理记录时，显示相应状态与已确认小时数，不按低比例标记闲置；应填工时为 0 时比例显示“不适用”，仍展示实际工作及加班小时数
- 筛选：部门、职级
- 下钻：点击单元格查看该人该周时间构成及确认状态

**口径验算**：4 小时项目工作 + 1 小时部门事务 + 3 小时待分配，应填 8 小时；全部确认后填报完整度为 100%，工作负荷为 5 / 8 = 62.5%，已确认待分配为 3 小时。半天请假、另工作 4 小时，应填基数为 4 小时，负荷为 100%，请假不再次加入分子。

**报表二：项目标准成本报表**
- 维度：项目
- 指标：累计已审批项目工时、标准人工成本、已审批现场天数、标准现场成本、标准总成本、参与人数（已锁定记录同样纳入统计）
- 现场天数独立按已审批现场日统计，包含因项目需要驻留休息而无工作工时的日期；不能因人员没有工时条目而漏掉其现场天数、成本与项目参与记录。实际发生的出差交通按项目工时另计标准人工成本
- 支持按月/季度/年区间、项目类型、**主责部门**筛选
- 部门负责人视角默认过滤为「本部门为主责单位的项目」
- PM 视角限定为本人负责项目，允许查看项目下各参与人的工时、采用的标准费率与成本明细，不按参与人的所属部门过滤
- 下钻：项目 → 人员 → 工时明细
- 正式月报按 6.6 保存版本，显示核算月份、版本号、生成时间与数据截止时间，支持查看原版及修订版；封账前的在线试算明确标识为“未封账”
- 月报同时提供未决清单，列出草稿未提交、待审批、驳回未处理和争议未解决记录及状态。未决工时、现场日不计入已确认成本，并明确提示“仍有未决数据”；缺填人员与日期也另行列示，不能将缺失数据视为已确认零投入

**报表三：现场日项目工时占比**
- 定义：`该出差事由项目当日实际工作工时 ÷ 当日实际工作总工时`；待分配与请假均不进入分母。仅在相关时间记录完整、审批完成且分母大于 0 时给出正式比例，否则显示待确认或不适用
- 分子与分母均按统一工时口径包含出差交通投入，因此该比例反映时间投入的项目归属，不直接衡量产出或效率
- 维度：项目、人员、月份
- 用途：复核现场期间的时间分配，结合跨项目支援安排和现场事由解释；合理支援其他项目不直接认定为低效
- 低于 50% 的记录提示“需复核时间分配”，不直接标为低效，不据此自动驳回工时或扣减成本
- 已确认因项目需要驻留休息且无工作工时的日期，比例显示“不适用”并展示现场事由，不按 0% 计入比例汇总或触发低占比提示；对应已审批现场天数和成本仍完整计入项目。已发生交通但未填交通工时的记录仍属于待完善数据
- 按项目、人员或月份汇总时，使用符合统计条件的记录之本项目工时合计除以实际工作总工时合计，不对各日百分比简单平均

**报表四：现场日台账**
- 维度：人员 × 日期
- 字段：日期、姓名、工号、部门、现场归属项目、现场事由说明、审批状态、标准现场成本、当日本项目实际工作工时/实际工作总工时、**OA 出差单比对结果**
- 比对结果取值：一致 / OA无单 / OA有单未填现场 / 项目不符（详见 5.5）
- 异常记录默认置顶并标色，支持只看异常
- 支持按人员、项目、部门、月份筛选，支持导出 Excel
- 用途：月度复核现场成本真实性

**报表五：填报与审批合规看板**
- 指标：各部门填报及时率、逾期提交人数、审批超时包数、超时审批人名单
- 同时统计封账未决记录、解锁补录或更正次数，以及月报修订次数，支持追溯处理原因
- 用途：部门月度经营会通报，是审批闭环落地的主要抓手

**数据导出**：全部报表支持导出 Excel。页面、下钻及导出均执行相同的项目和字段权限，PM 只能导出本人负责项目范围内获授权的标准成本信息。正式月报导出包含月份、版本号、生成时间及数据截止时间；导出原版必须使用该版本保存的报表数据与未决清单，不能替换成最新处理结果。当前处理进度可单独查询。

### 6.5 提醒与催办（P0）

| 场景 | 时间 | 接收人 | 渠道 |
|---|---|---|---|
| 当日填报提醒 | 工作日 17:30 | 当日未填报者 | 企微应用消息 |
| 补填提醒 | 次日 10:00 | 前一日未填报者 | 企微应用消息 |
| 连续未填报告警 | 连续 3 日未填 | 员工本人 + 部门负责人 | 企微应用消息 |
| 周提交提醒 | 次周一 10:00 | 上周记录未提交者 | 企微应用消息 |
| 审批待办 | 次周一 14:00 | 有待审批包的实际审批人 | 企微应用消息 |
| 审批截止前提醒 | 次周三 15:00 | 仍有未处理待办的实际审批人 | 企微应用消息 |
| 审批超时升级 | 次周四 09:00 | 实际审批人 + 其上级 | 企微应用消息 |
| 驳回通知 | 实时 | 被驳回员工 | 企微应用消息 |

消息需带跳转链接，点击直达对应页面。

**提醒配置化要求（P0）**：上表中的全部时间点、触发阈值与开关，**必须由管理员在后台可配置，不得硬编码**。需提供「提醒规则管理」页面，每条规则支持配置：

| 可配置项 | 说明 |
|---|---|
| 启用开关 | 单条规则可独立开关 |
| 触发时间 | 具体时刻，如 17:30 |
| 触发日类型 | 工作日 / 每日 / 每周指定星期 / 每月指定日 |
| 阈值参数 | 如"连续未填报天数"、"审批超时天数" |
| 接收人范围 | 本人 / 本人+直属领导 / 本人+部门负责人 |
| 消息模板 | 支持变量占位符，如 `${姓名}` `${日期}` `${待办数量}` |

同理，以下参数也需纳入系统参数配置，不得硬编码：单日工时上限（24h）、红标阈值（16h）、默认应填基数（8h）、工时步长（0.5h）、周提交截止时点、审批截止时点、封账日（10 日）。

> 试用阶段几乎必然要调整提醒节奏——推早了没人理，推晚了来不及改。这些参数写死会导致每调一次就要发一次版，试用期迭代成本极高。

### 6.6 封账、解锁与月报修订（P1，已确认）

**月度封账**：

- 每月 10 日 00:00 封闭上月，日期由管理员配置。按工时及现场日的发生日期归属月份，已确认工时与现场日一起置为 `locked`，按同一数据截点生成正式月报首版。
- 草稿未提交、待审批、驳回未处理和存在未解决争议的记录保留原状态，单列未决清单，不计入已确认成本；存在未决或缺填数据时，月报必须明确提示数据尚未全部确认。
- 封账约束作用于整个核算月份。员工、PM 和同步任务均不能未经授权直接新增、补审或修改该月份的业务数据；OA 迟到或更正数据保留为待处理差异，不直接改动历史工时、现场日、应填基数或已发布月报。
- 跨月审批包按条目发生日期分别遵守各月份的封账状态，整包操作不能绕过已封账条目的授权要求。

**封账后处理**：

1. 补录、补审或修改必须说明原因，并明确人员、日期、记录及处理范围；补录时即使原记录不存在，也须授权相应人员与日期范围。
2. 按 2.2 的既有权限，由有权的部门负责人、分管领导或管理员授权解锁指定范围，记录授权人、时间和原因；其余数据仍保持封闭，解锁不等于审批通过。
3. 原待审批记录获准后继续审批；新增或更正记录按既定路由提交或重新审批，本人回避规则继续适用。保留原始数据、修改前后内容、处理依据和审批记录；仅有解锁授权而未获业务审批的金额不能计入确认成本。
4. 本次修订涉及的记录处理完成后，将本次获批的工时与现场日重新置为 `locked`，关闭对应解锁范围，生成新的月报版本。其他记录保留其实际审批状态并继续受月份封账约束，不能为关闭解锁范围而自动通过。新版标明修订原因、关联原版本及前后差异，原月报和原未决清单保持只读；其他未解决记录仍在新版未决清单中列示。

**版本与查询**：正式月报可选择原版或修订版，默认展示最新已发布版本并明确标记版本号。解锁或更正处理中不会改变当前已发布版本；查看当前处理进度时应明确标识其尚未纳入新版本。解锁、更正和月报修订全程留痕，并在合规看板单独统计。

**验算场景**：8 月的一笔工时在 9 月 10 日封账时仍待审批，列入 8 月月报首版的未决清单。9 月 12 日获准补审并通过后，重新锁定该记录，生成 8 月月报修订版并展示增加的工时及成本；首版金额和当时的未决清单均不改变。

## 7. 系统集成

### 7.1 企业微信（P0，硬依赖）

| 集成点 | 说明 |
|---|---|
| 通讯录同步 | **仅同步人员身份信息**（姓名、UserID、在职状态），每日一次 + 手动触发；工号复用现有身份关联取得。组织结构与部门负责人由管理员在本系统维护，v1 不同步 |
| 免登认证 | **内部已实现企业微信自建应用 SSO，本系统复用现有 SSO 并完成接入验证**，员工无需单独账号密码 |
| 应用消息 | 全部提醒与催办通过自建应用消息推送 |
| 工作台入口 | 应用挂载于企微工作台，支持移动端与 PC 端 |

**已确认条件**：内部企业微信自建应用 SSO 已实现，企微 UserID 与工号之间的关联已打通。本项目以接入现有能力为基础，具体接入协议与身份字段由信息部门提供，不预设 SSO 必须直接返回工号。

**接入核对范围**：确认本系统接入现有 SSO 的方式、目标环境工作台入口与域名/网络配置，以及通讯录读取、应用消息发送所需的权限和配置。SSO 已实现不代表上述同步与消息能力已经完成，也不替代本系统内的角色和数据范围授权。

**审批实现方式**：审批流在自建系统内实现，不使用企微原生审批。原因：原生审批的数据回写与状态同步复杂，且无法承载按对象拆包的审批逻辑。企微仅承担身份认证、消息触达与入口。

### 7.2 金蝶苍穹 OA（已确认数据开放）

信息部门已确认苍穹数据可开放，并由**信息部门按本系统要求开发 RESTful 接口**。详细字段与技术规格见配套文档《苍穹接口需求规格书》。

**接口清单**

| # | 接口 | 用途 | 优先级 | 同步频率 |
|---|---|---|---|---|
| 1 | 项目立项查询 | 项目主数据同步 | P0 | 每日 02:00 增量 |
| 2 | 请假休假查询 | 计算当日应填工时基数 | P0 | 每日 01:00 + 实时补拉 |
| 3 | 出差申请查询 | 现场日月度比对 | P1 | 每月封账前 |

**已确认苍穹不提供**：人员岗位与职级数据。因此职级（初级/中级/高级）由管理员在本系统内维护，费率体系不依赖外部系统。

**集成原则**

1. **拉取模式，非推送**。由本系统定时主动调用苍穹接口，苍穹只提供只读查询服务。理由：拉取可重试、可补偿、可回溯，苍穹侧无需改造消息机制；推送模式一旦本系统故障，消息丢失后无法自愈。
2. **单向只读**。本系统绝不向苍穹写入任何数据，避免污染 OA 权威数据源，也降低信息部门的评审阻力。
3. **手工兜底必须保留**。全部同步数据都有对应的手工维护或 Excel 导入路径，接口故障或延期不影响系统可用。
4. **同步失败不阻塞主流程**。同步任务失败仅告警至管理员，员工填报与审批照常进行。

**人员与部门标识对齐**

人员身份关联已具备基础能力，本系统按以下关系接入：

```
苍穹（工号） → 本系统 user.employee_no → user.id → 工时 / 审批 / 成本
企微 SSO（UserID） → 已有 UserID—工号关联 → 同一条 user 记录
```

- 苍穹返回的 PM、请假人、出差人均通过工号匹配本系统人员。工号字段统一按字符串接收、导入和导出，支持五位数字与两位字母加五位数字两种格式，不转成数值或截取数字部分
- `employee_no` 用于外部匹配，`user.id` 是内部稳定的自增主键；所有业务关联保存 `user.id`。企微 UserID 与工号是否相同不影响接入，使用现有已打通的关联能力即可
- 工号变更保持同一 `user.id`。若苍穹迟到数据或历史补拉仍携带旧工号，应解析回原人员；旧工号解析能力需在接入核对时确认，无法解析的记录进入异常处理，不自动新建人员或按姓名合并
- 部门标识仍需单独核对：苍穹返回部门编码，本系统 `department.code` 需与之对齐，或维护映射表

> 人员关联已打通是已确认事实。联调重点是复用既有身份能力、验证两种工号均能定位同一内部人员，以及工号变更后的历史数据处理，不再以新建人工映射体系为项目启动前提。

### 9.1 开发里程碑

| M2 | 审批包拆分、审批流、本人回避与转交、驳回及争议处理、企微消息推送 | 填报—审批闭环打通 |

**M5 与 M1-M4 并行推进**：接口需求规格书应在 M1 阶段就交付信息部门，由其排期开发；本系统侧同步实现同步任务框架与手工兜底路径。M1-M4 全程使用 Excel 导入数据开发与自测，M5 仅做数据源切换与联调，接口延期不影响前四个里程碑交付。

### 9.2 上线策略

按业务方确定的节奏：**全功能开发完成后先小范围试用，工作流全部理顺后再全员使用。**

*试用阶段（建议 4 周）*
- 范围：1-2 个二级部门，含至少 2 名 PM、1 名部门负责人
- 目的：验证审批链是否跑得通、填报耗时是否达标、报表口径是否符合管理需求
- 关键观察项：PM 是否真的按时审批（这是整套机制成败的关键，不是技术问题）
- 出口标准：连续 2 周填报及时率 ≥ 90%、审批完成率 ≥ 90%、报表数据经人工抽查核对无误

*全员推广*
- 试用出口标准达成后启动
- 需配套发布《工时填报管理办法》，明确填报义务与审批责任
- 首月每周通报合规看板数据

### 9.3 配套管理机制（需与系统同步落地）

系统本身无法解决审批闭环问题，必须配套以下机制：

1. **PM 的成本责任与事实核实**：经审批确认的实际项目工时按标准费率计入项目成本，并在部门月度经营会上呈现。审批核实投入是否发生、项目归属是否正确；效率问题另行复盘，不得为降低成本压减真实工时或转记杂活。存在争议时按 4.5 协调或裁定，保留原始记录与处理依据。
2. **合规数据进管理例会**：填报及时率与审批超时名单每月通报，这是唯一能让审批不流于形式的抓手。
3. **报表进决策**：人员负荷热力图与项目成本报表必须进入部门月度经营会议程。员工看到数据被使用，填报意愿才能维持。

> 建议不将工时数据与个人绩效奖金强挂钩。强挂钩会将问题从"没人填"转变为"精心造假"——员工会将工时往有预算的项目上转移，数据失真更隐蔽、更难纠正。

| # | 场景 | 预期结果 |

| 10 | 周末发生加班、交通或驻留，次周一提交 | 按发生日期归属上周，次周一 12:00 截止，14:00 推送待办，周三 18:00 审批截止；自动提交不绕过校验或重复提交已处理记录 |

| 12 | 8 月工时在 9 月 10 日仍未决，9 月 12 日处理 | 原版未决单列；获授权后补审或更正，处理后生成修订版，原版金额及未决清单可复现，工时与现场日均受封账限制 |
| 13 | 现场日为出差事由项目投入占比低于 50%，其余时间为合理跨项目支援 | 提示复核时间分配，不直接认定低效，不自动驳回或扣成本 |

| 现场日 | 因项目出差的自然日计费，含交通、必要驻留及半天按整天；每人每天一次，归主要事由；私人延长不计 |
| 审批 | 所有人工审批回避本人；逐级无法承接时由公司指定另一负责人；缺席或离职由管理员按业务指定转交并留痕 |
| 争议 | 核实事实与项目归属，效率另行复盘；由项目主责部门负责人协调，跨部门协调不成由分管领导裁定 |
| 周节奏 | 次周一 12:00 提交截止、14:00 推送审批待办、周三 18:00 审批截止，覆盖完整自然周，参数可配置 |
| 成本权限 | PM 可查统一职级费率及本项目人员标准成本明细；普通员工仅看本人工时；费率仅管理员维护 |
| 占比报表 | 使用“现场日项目工时占比”，低于 50% 只提示复核时间分配，不直接认定低效 |
| 封账 | 每月 10 日封上月，未决单列；授权后补录、补审或更正，修订版与原版均保留 |
