## 已验证的业务边界

- 工号 `98123`、`XX12345`、`ZD23412`、`00123` 及大小写字母按字符串保存；前导零保留；错误格式被拒绝。
- 新增人员后，工号更改继续使用同一个内部 ID；已有会话读取到新工号，随后恢复工号仍关联原人。
- 普通员工不能读取管理员费率接口，返回 403。
- 当天新建人员可当天授予及撤销 ADMIN；已有会话立即反映权限变化，撤销后费率查询返回 403。
- 当天新建人员可当天停用和恢复；停用后已有会话访问 `/me` 返回 401；恢复后 ID 不变。
- 工作日历修改与关联日记录在同一事务提交，日记录基数和版本号同步更新；旧版本草稿保存返回 409，不能覆盖新日历基数。
- 新费率保留四位小数，追加时将前条开放区间止日设为新起日；同起日标准返回 422；已到封账时点的历史标准写入返回 409。
- 工时金额直接按日标准 × 分钟 / 480 计算，每条记录 `HALF_UP` 到分后汇总，不预先将小时标准舍入；超时工作不加倍率；零分钟、非法步长和负标准被拒绝。

## 日历与请假重算补充验证

代码已修复，相关主数据 / 计价 / 日规则 24 例单元测试通过。最终 API 制品重启后，以下精准 HTTP + 真实 MySQL 回归已通过，脚本退出码为 0：

```sh
python3 scripts/verify-calendar-leave.py
```

复现场景使用独立新人员及唯一测试来源：原始已批准请假为 240 分钟，将测试日期设为休息日后保存草稿，此时派生日记录中的基数、请假、应填分钟都是 `0 / 0 / 0`。再将该日期改为 480 分钟工作日，必须从 `leave_record` 原始来源重新计算，使数据库缓存与 API 都成为 `480 / 240 / 240`，且日版本号增加。不能沿用已截为零的旧请假缓存。

日历维护在同一事务内先锁日期和对应日记录，再按人员查询已批准的来源，复用 `DayRules.leaveMinutes` 进行校验、去重和基数截取。脚本结束时撤销其测试来源、恢复日历并停用测试人员，不改预置人员的填报内容。

本次实际运行使用测试人员 ID `15`、日期 `2026-10-22`：休息日保存后持久化值为 `0 / 0 / 0`；变更为工作日后 API 与数据库均为 `480 / 240 / 240`，日版本增加，原始来源仍为 240 分钟。清理流程正常完成。

## 导入服务只读审查

本轮另检查了来源版本、批次权限和事务边界，没有修改导入模块。审查确认预览只保存批次、原始行和审计；封账范围的应用失败保留来源差异，同时回滚业务变化；批次读取及应用需要 ADMIN；请假应用遵循月份、日期、人员 / 日记录、来源的加锁顺序。

审查发现一种旧来源回退情形：早先接收但失败的批准版本，可能在较新版本已撤销后通过重试恢复请假。导入模块已补充来源父行锁内的校验，对比本地首次接收序号与当前来源头，拒绝被后续版本取代且从未应用的旧记录；不解析或比较外部版本号的数值大小。已经应用过的旧版本重复接收仍只作幂等确认。导入模块另行完成真实 MySQL 回归：未知工号的 v1 先失败，建档后 v2 批准、v3 撤销，再重试 v1 被判为过期来源，`leave_record` 保持 REVOKED。

## 当前边界

- 此阶段人员、组织、归集对象、费率及日历维护为系统管理员权限；部门负责人维护非项目事项的范围权限随后续业务模块完成。
- 新人员和部门 / 职级变更的 `effectiveFrom` 必须为已生效日期；未来费率可以追加。现有人员启停与权限变动立即生效，不能用旧生效日期阻止紧急停用或撤权。
- `revoked_at` 用于当前权限撤销判断；`reporting_enrollment.voided` 用于排除当天取消的适用区间。重建历史权限时需结合授权 / 撤销事件时间，不应把当前撤销标记当作从未授权。
