## 1. 实施目标与边界

交付一个能用于真实业务试点的完整 MVP：员工在企微 H5 或电脑端记录工作与现场日，责任人核实，系统按发生日标准确认项目成本，管理层同时查看项目投入与人员负荷，并能封账、授权更正及追溯历史月报。

实现沿用已确认的技术架构：H5 使用 Vue 3 + Vant，Admin 使用 Vue 3 + Element Plus 的 Vue3 Admin 形态；两端共享 API。后端使用 Java 21、Spring Boot + WxJava、Spring JDBC / JdbcClient、Flyway，数据使用 MySQL 8.4 与 Redis。API 和 worker 由同一后端制品按不同 profile 启动，Nginx 同域提供 `/h5`、`/admin`、`/api`，采用 Docker Compose 部署。

现有企微 SSO 与 UserID—工号关联直接复用。人员使用内部自增主键，`employee_no varchar(20)` 保存字符串工号。具体依赖补丁、Redis 版本、Node.js 版本及 Admin 模板在首次构建验证时锁定，执行本计划不重新选择另一套后端。

首版交付范围包含 P01–P11、五项报告能力、AT01–AT18，以及正式月报、授权修订和必要运维能力。手机端覆盖填报、审批和本人记录；管理与分析由 Admin 承担。以架构的双前端决定为准。

不扩展薪酬核算、实际报销、预算毛利、任务 WBS、通用流程编排、WPS 历史迁移或新的身份平台。只创建当前任务需要的代码与表，不先搭建通用框架。

### 1.1 执行中的固定约束

1. **月份控制先于业务写入。** A 阶段完成门禁基础，封账页面虽在 D 阶段，保存、审批和来源数据应用从首次实现即受月份约束。
2. **计价先于首次通过。** A 阶段实现历史标准与唯一计价函数，B 阶段通过时原子保存成本快照，C 阶段完成分析展示。
3. **权限随功能交付。** 每个查询、变更及导出任务都包含对应角色、数据范围和字段校验，不能留到末尾统一补权限。
4. **工时与现场日分别闭环。** 送审、驳回、计价、取消和更正均覆盖“只有现场日、没有工时”的日期及整周。
5. **接入结果如实标记。** 样例验证、真实接口联调、人工导入兜底是不同状态；使用兜底不能把自动接入任务标为完成。
6. **试点前完成完整闭环。** 不以登录、页面或单次审批演示代替 A–D、恢复演练及业务验收。

## 2. 工作组织与里程碑

表中的负责人是职责，不代表已配置人员。开工时由项目负责人把任务分配给具体执行人；一人可承担多个职责。质量验证可由开发交叉执行，最终业务口径由业务代表核验，不要求额外建设项目管理系统。

| 职责 | 主要责任 |
|---|---|
| 项目负责人 | 维护依赖、任务状态、交付范围与实际排期；组织阶段演示和试点启动 |
| 后端负责人 | 数据约束、领域规则、事务、权限、集成、任务、接口与迁移 |
| 前端负责人 | H5 / Admin 及共享 API 客户端，异常交互、业务页面和两端联调 |
| 验证负责人 | 维护验收数据、AT 记录、权限与并发检查、性能及回归证据 |
| 信息部门 | 现有 SSO 契约、企微权限、OA 接口与联调窗口；配合身份异常处理 |
| 运维负责人 | 测试与生产环境、网络证书、密钥、发布、备份恢复与运行保障 |
| 业务代表 / 管理员 | 组织、路由、日历、费率与来源数据核实；试点数据维护及业务验收 |

| C：管理分析 | 三个视图承载五项报告能力，权限、Excel 与来源比对 | B03 能产出可靠确认事实；不必等待全部 B 页面完成再写查询 | C04：人工核对明细与汇总，角色和导出范围一致；现场 OA 比对另由 E06 验收 |

A–D 是交付检查点，不要求开发按整阶段串行等待。E01 / E04 契约收集开工即做；R01 环境准备在首个制品可用后做；C01 可在 B03 后启动，D01 可在 C01 后启动。业务端到端路径尽早连通，后续补齐全部角色和例外。

### 2.2 排期与进度口径

当前缺少团队可用投入和真实接口窗口，因此本版不承诺自然周工期。开工安排人员后，以第 3 节依赖排序估算任务工作量与等待时间；A09 完成后，用实际交付速度更新 B–D 和 R 的完成日期。OA 外部等待单独记录，不能当作开发工作量，也不能悄悄改变上线范围。

每个执行中的任务只记录：具体负责人、状态、计划完成时间、实际阻碍和证据链接。状态为“待开始 / 进行中 / 受阻 / 待验收 / 已完成”。本版编制时全部任务初始为待开始，开工后的实际状态记录在[开发进度](../development/首批本地开发验收.md)；阶段未验收前不能因代码完成自动变成已完成。

每天更新正在推进及受阻任务；每个交付节点演示一次完整业务场景即可，不另建重复周报或多套看板。若只有一名执行人，仍按依赖推进，不假定具备并行人力。

## 4. 关键实现与验收门槛

### 4.1 数据与权限基础：A 阶段必须落实

- `user.id` 稳定；五位数字和两字母加五位数字工号均按字符串保存，前导零、换工号、旧工号来源重放有明确处理。不能按姓名合并或把换工号当作新人。
- 人员归属、职级、费率和对象历史按半开区间处理；先锁稳定父记录再校验重叠。验收要包含并发新增区间，不能只证明单次表单校验。
- 日记录使用版本号；工时与现场日有独立主体及内容版本。保存、基数变化、审批变化等按架构更新日版本，旧页面收到冲突时保留输入并提示刷新。
- 后端显式使用 `READ COMMITTED`，固定“月份 → 主数据父记录 → 日记录 → 审批包 / 项”锁顺序。月份行在填报前存在；截止条件使用数据库时间，不能仅依赖定时任务更新状态。
- 员工本人接口不返回费率 / 金额。PM 看本人项目所有参与人；部门人员负荷范围和主责项目成本范围分开判断。指定审批权不扩大整项目报表权限。
- 内部 ID 与金额按约定输出字符串，分钟为整数；业务日期按 Asia/Shanghai，操作时间统一存 UTC。两端共用类型与错误码，不各自换算业务规则。

### 4.2 填报与审批：B 阶段必须形成可追溯事实

日校验使用全日当前记录，而不是仅本次修改的条目。应填基数、24h 上限、0.5h 步长、实际工作超过 16h 的说明、内容规则及部分驳回重提均由后端执行。6h 已通过、2h 驳回的例子应按全日 8h 校验，重提只产生这 2h 的新审批项。

审批前预览不替代提交时再次校验。一个工时版本最多一个审批项，同一人一天最多一个当前现场日。工时与现场日各自送审和计价；必要驻留可以为零工作，不补造 8h 工作。改地点不能直接删掉已送审或已确认的现场日。

通过时使用发生日职级与标准：人工金额为日标准乘本条分钟数再除 480，逐条按 HALF_UP 保留两位。先逐条得到金额再汇总；非项目和待分配不产生项目成本。状态、成本快照、处理人、审计和 outbox 必须同事务提交，外部消息提交后发送。

更正创建新版本，不覆盖已处理内容；新版本通过前从当前确认金额排除旧版，旧月报仍保持原值。日期错误按取消原记录和新增正确日期处理，跨月分别检查授权。转交仅改变待处理项，不改旧处理人、不延长截止时间。争议仅阻止相关项，协调结论不直接重写工时事实。

### 4.3 报表与封账：C / D 阶段必须保留一致截点

三视图必须覆盖人员负荷、填报 / 审批合规、项目标准成本、现场占比、现场日台账五项能力。负荷、成本、加班与现场比例采用各自既定分子分母；缺填 / 未决不能显示为已确认闲置，零分母显示不适用，比例汇总不能平均每天百分比。

D01 在一个月份独占事务内冻结整月数据，按架构使用单个一致取数语句保存规范化快照行，后续汇总只读冻结行。保存展示值、口径版本、来源覆盖以及应有人日，即使预生成任务失败、无人填报也能识别缺填。文件生成在事务提交后进行。

解锁是明确动作和范围的授权，不是把整个月份重新开放。每月最多一个活动修订批次，可含多项范围。新版发布时重新冻结整月、记录差异并关闭范围；未通过项继续未决。旧版访问仍按当前权限，但内容始终读取原快照。

导出申请、生成和下载分别核查当前权限。文件私有保存，权限缩小导致文件含越权范围时拒绝原文件下载并要求重新生成，不能只在按钮处隐藏入口。临时文件清理不删除正式报告事实、审计或来源证据。

### 4.4 后台任务与生产运行

任务及通知的唯一业务状态存在 MySQL；Redis 只承担会话和短期缓存。重试不能重复提交、扣假、计费或发布。企微超时且送达结果未知时保留实际状态，不宣称外部消息绝对只送达一次。

最低运行检查包含 MySQL / Redis 可用性、worker 心跳、到期未执行任务、同步覆盖、通知积压、封账失败、最近备份和磁盘空间。Redis 故障不能绕过身份校验；worker 停机不能放开旧月份写入。工作日服务保障之外，夜间封账和备份仍需运行。

| AT13 | C01、C02、C04、E06 | 小于 50% 只提示、零工作不适用、汇总按总分子 / 总分母 |
| AT14 | A08、B02、B04、B05 | 基数不足、24h、16h 说明、内容规则、6h + 2h 部分重提 |
| AT15 | A06、A07、D02、D05、E05 | 封账后新增 / 补审 / 基数变化、跨月包、迟到来源范围 |
| AT16 | E02、E05、E06、E07 | 接口失败 / 覆盖不明不误报，核实导入可运行，不自动造现场 |
| AT17 | A06、A08、B01、B03、B04、D01、D05、E02 | 重复命令与并发无重复成本 / 版本，改地点必须走规则 |
| AT18 | A04、A05、D03、D05、R03 | 历史组织 / 费率 / 月报可复现，业务与审计共同恢复 |

AT 验收允许按既定兜底路径验证对应业务，但 E05 / E07 的真实联调另记结果。AT16 使用失败样例证明异常行为，不等于 OA 生产来源已就绪。

### 7.3 必要技术验证

| 类别 | 执行方式 | 通过依据 |
|---|---|---|
| 业务计算 | JUnit / Spring Boot Test 的关键边界样例 | 发生日取值、逐条舍入、负荷、加班、现场比例有人工独立预期 |
| 数据与事务 | Testcontainers 或隔离环境中的真实 MySQL 8.4 / Redis | 唯一约束、锁、隔离级别、回滚、重试有可复现结果；不用 H2 替代 |
| 权限 | 表驱动角色 / 数据 / 字段矩阵 | 列表、详情、搜索、聚合、导出生成、历史版本和下载撤权全部覆盖 |
| 外部接入 | 固定异常样例 + 真实测试接口 | 幂等、撤销、游标、覆盖和映射异常可追踪；记录实际环境与接口状态 |
| 两端闭环 | 少量 Playwright 关键路径 + 企微真机检查 | 日记录 → 核实 → 成本 → 封账 / 更正 → 新旧版导出；手机填写 / 审批可用 |
| 构建与迁移 | 类型检查、生产构建、后端验证、空库及既有测试库升级 | 制品可重复生成，数据库结构兼容，迁移失败不带病发布 |
| 运行恢复 | 发布演练、异机备份恢复、worker / Redis 故障演练 | 数据核对完成、故障影响明确、恢复操作可执行 |

并发与失败至少覆盖以下七组场景：

1. 同一人两个页面写同一天：旧版本至多一个成功，日总量不穿透。
2. 重复通过与转交同时发生：只有一个结论，旧接收人不能继续处理，实际处理人准确。
3. 手动与自动周提交重叠：一个内容版本只生成一个审批项。
4. 审批与封账竞争：整笔进入快照或保留未决；worker 延迟时月份时点控制仍有效。
5. 零工时独立现场送审与驳回：现场状态及成本完整，不依赖工作条目。
6. 封账提交后进程退出、回执丢失：重试读取已有版，不再次发布。
7. 已确认记录更正：新版本未通过时排除当前旧金额，已发布版本原值不变。

R02 以峰值 100 人同时填报、约一年业务数据量测试常规保存 / 查询，目标响应 <1 秒；记录端到端计时范围、分位数、错误率、数据库耗时与锁等待。采用架构中的初始容量假设作为压测起点，不宣称已满足指标。Excel 与封账单独计时，不混入日常保存指标。性能未达标先定位 SQL、索引、事务和资源，再决定必要调整。

每个任务的完成证据至少能指向对应代码 / 迁移、适用验证结果和演示记录。简单维护页面不要求机械复制 CRUD 测试；高风险计算、事务、权限和历史一致性必须有自动化或可重复验证。测试通过后只对新改动、失败或未解决问题继续扩大验证范围。

## 8. 发布与试点执行

### 8.1 试点启动门槛

R04 前逐项核对，未完成项保留为阻碍，不用“基本可用”替代：

- A09、B07、C04、D05 均完成，P01–P11 和五项分析能力可用，AT01–AT18 及必要技术检查有结果。
- 影响事实、金额、权限、幂等或历史版本的已知缺陷已修复并回归；其他遗留项明确影响和处理时间。
- SSO、两种工号、真实角色、本人回避、企微消息及手机网络已验证；生产没有测试登录入口。
- 每个 OA 来源已真实接入或按第 6 节由具名人员执行核实导入；不存在影响试点事实的未知覆盖。
- 初始化真实人员、适用区间、组织、对象、职级 / 费率历史、请假、日历、回避链及提醒参数，测试金额不进入实际核算。
- 部署、备份恢复、监测及故障处理完成演练，确认值守人与数据维护人；审计和报告历史不会按 30 天备份周期清理。
- 确定 1–2 个部门、至少 2 名 PM 和 1 名部门负责人；开始日期覆盖一次真实月度封账，并安排一次管理会议使用数据。

### 8.2 发布步骤与停止条件

| 顺序 | 执行动作 | 必须检查 |
|---|---|---|
| 1 | 固定后端镜像、H5 / Admin 制品、迁移版本和配置版本 | 来自已验证的同一发布批次，密钥外部注入 |
| 2 | 备份 MySQL 及需留存的来源证据、恢复配置 | 备份在另一故障域可访问；确认恢复方式 |
| 3 | 单次运行 Flyway 迁移 | 独立迁移账号和发布步骤；失败则停止后续发布 |
| 4 | 发布相互兼容的 API、worker、H5、Admin | API / worker 职责分离、数据库兼容；入口和静态路由正常 |
| 5 | 执行登录、保存、核实、查询和任务健康冒烟 | 生产使用预先安排的真实受控业务记录；不将虚构工时或测试费率写进正式成本 |
| 6 | 记录结果并开放试点入口 | 有异常则暂停新业务操作，按演练方案回退或前向修复 |

发布前在测试环境完整演练审批与月报；生产冒烟不得为验证而伪造事实。代码回退必须与当前数据库结构兼容。涉及数据库恢复时先阻止继续写入、保全故障后的业务证据并确认影响，不能把回退旧镜像误当作数据已恢复。

每日全量备份保留 30 天，试点前实际恢复。恢复记录注明备份时间、恢复耗时、核对对象和差异；按该基线最坏可能接近 24 小时的数据恢复点。更小恢复窗口另行按实际要求增加 binlog 归档，不在首版假定已经具备。

### 8.3 试点期间与出口

| 时段 | 执行重点 | 证据 |
|---|---|---|
| 启动前 | 员工演示填报 / 现场，PM 演示核实 / 回避，管理员演示差异和月报 | 各角色能独立完成核心动作，责任名单齐全 |
| 第 1 周 | 观察真实日填报、来源更新、通知、驳回和跨部门核实 | 输入耗时、错误原因、缺填及待办清单；优先修复影响事实和操作的问题 |
| 第 2–3 周 | 连续跟踪及时率、完成率和人工成本 / 负荷对账 | 按当时规则及事件统计，保留分子、分母和未决；补填不倒改历史及时率 |
| 实际封账日 | 正式生成试点范围月报，核对缺填、未决、现场与确认金额 | 一次真实封账、正式版本、人工核对和任务记录 |
| 第 4 周或顺延期 | 用测试数据演示授权更正和 V2，安排至少一次管理会议使用真实数据 | V1 原值、V2 差异，实际核实 / 调整事项及试点结论 |

试点出口沿用产品设计：连续两周填报及时率 ≥90%、审批完成率 ≥90%，常规日填报 ≤3 分钟；人工抽核工时、负荷、现场日、费率与金额无误；完成真实封账和修订演示，至少一次会议使用成本及负荷数据。没有覆盖真实月度封账则顺延，不能用模拟封账代替这一项。

扩大到全员运行时，及时率和审批完成率目标为 ≥95%，另按试点结果安排推广。若数据虽及时但缺乏事实核实，先修正责任和管理执行；若接口仍靠导入，明确持续维护负担及剩余接入计划，不通过增加页面掩盖问题。
